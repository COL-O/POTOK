# Карта доступов: что может агент, где это настраивается

Зафиксировано по факту проверки 2026-11-15 (Сфера). Цель: чтобы цифровой соратник мог не только код и файлы, но и **добавлять обсуждения и настраивать общение** сам.

## Как агент подключён сейчас

- Агент действует в GitHub через **интеграцию Arena (GitHub App)**: в песочнице стоит служебный токен-заглушка, реальные права выдаёт приложение Arena, установленное на аккаунт владельца.
- Проверка фактом: `api.github.com/user` отвечает от имени владельца, пуш и CI работают, но ряд действий интеграция запрещает: **`403 Resource not accessible by integration`** — на изменение описания репозитория, включение Discussions (уже включено владельцем вручную) и создание обсуждений (`createDiscussion`).

## Что агент может сейчас — проверено действиями 2026-11-15

| Действие | Результат проверки |
|---|---|
| Код: коммит и пуш в рабочую ветку, CI смотреть | ✔ работает |
| Issue: создать, закрыть, комментировать | ✔ работает (служебный Issue №3 создан и закрыт проверкой) |
| Метки: создать/удалить | ✔ работает |
| Issue: закрепить (Pin) | ✔ работает — общий чат закреплён: Issue №4 |
| **Discussion: создать ветку** | ✖ `403 Resource not accessible by integration` |
| **Discussion: ответить в ветке** | ✖ `403` (проверено на ветке №2 владельца) |
| **Описание/настройки репозитория (PATCH)** | ✖ `403` |

Вывод по факту: доступ широкий, но отсутствуют ровно **два разрешения приложения — Discussions и Administration**. «Полные настройки» в интерфейсе Arena и список разрешений GitHub App на GitHub — два разных слоя: первый разрешает приложению действовать, второй — что именно приложение вправе делать на GitHub. Если строки *Discussions* нет в списке Permissions на странице Configure (см. ниже) или она Read-only, владелец не может её добавить сам: разрешения задаёт разработчик приложения; GitHub показывает владельцу только запрос на одобрение, когда разработчик обновит приложение.

### Подтверждено скриншотом владельца (2026-11-15)

Владелец открыл страницу приложения Arena (GitHub → Settings → Applications → Installed GitHub Apps → Configure). В блоке «Разрешения» ровно две строки:

- **Чтение**: проверки, статусы коммитов и метаданные (Checks, Commit statuses, Metadata — Read);
- **Чтение и запись**: действия, код, вопросы (Issues), запросы на вытягивание (Pull Requests), рабочие процессы (Actions, Contents, Workflows — Read and Write).

Строк **Discussions** и **Administration** в списке нет вообще. «Репозиторий доступ» стоит на максимуме — «Все репозитории». Итог: тумблеров, которые владелец мог бы включить для Discussions, на этой странице не существует; разрешение появится только если Arena добавит его в приложение и владелец одобрит обновление (GitHub покажет запрос на той же странице и пришлёт письмо).

На переходный период живой общий чат соратников работает как **закреплённый Issue №4** — туда агент писать может, и уже написал приветствие.

## Где расширяется доступ (делает владелец)

### 1. Разрешения приложения Arena на GitHub

Путь: аватар → **Settings** → **Applications** → **Installed GitHub Apps** → приложение Arena → **Configure**
(официальная инструкция GitHub: «Reviewing and modifying installed GitHub Apps», docs.github.com/en/apps/using-github-apps/reviewing-and-modifying-installed-github-apps).

На странице Configure проверить два блока:

- **Repository access** — выбран репозиторий `COL-O/POTOK` (или All repositories).
- **Permissions** — какие права у приложения сейчас. Для полной работы соратника нужны:
  - *Contents* — Read and write (уже есть: пуш работает);
  - *Issues* — Read and write;
  - *Discussions* — **Read and write** (создание обсуждений и ответов, отметка ответов в Q&A);
  - *Pull requests* — Read and write;
  - *Administration* — Read and write (описание, темы, настройки репозитория) — самое широкое право, выдавать осознанно.

⚠️ Честное ограничение: список прав в Configure задаёт **разработчик приложения**, владелец может только принять или отклонить то, что приложение запросило. Если пунктов Discussions/Administration там нет или они не меняются — расширить их с GitHub-стороны нельзя; тогда нужно, чтобы Arena обновила разрешения приложения, а владелец одобрил обновление (GitHub пришлёт письмо/покажет запрос на той же странице Configure). До тех пор эти действия остаются ручными за владельцем.

### 2. Переподключение GitHub в Arena

Если в Arena есть экран подключённого GitHub (приложения/коннекторы) — переподключить GitHub там после шага 1, чтобы Arena подхватила обновлённые права.

## Что не даст даже широкий доступ (ограничение платформы)

Проверено по списку мутаций API: у GitHub **нет** API для создания/переименования категорий Discussions и для закрепления обсуждений (Pin). По документации категории управляются из интерфейса людьми с доступом write и выше. Поэтому, независимо от прав агента:

- категории Discussions создаёт/переименовывает владелец: вкладка **Discussions** → ⚙ у «Categories»;
- приветственное обсуждение закрепляет владелец (**Pin discussion**), готовый текст — [`WELCOME-DISCUSSION.md`](WELCOME-DISCUSSION.md);
- если агент получит Discussions write, он сможет сам **создавать обсуждения и отвечать**, но не настраивать категории.

## Практический итог

| Действие | Кто может сейчас | Что нужно |
|---|---|---|
| Код, файлы, шаблоны, документация | Агент ✔ | — |
| CI, проверка прогонов | Агент ✔ | — |
| Создать обсуждение, отвечать, отмечать ответ | Владелец | Discussions: Read and write у приложения (шаг 1) или вручную |
| Описание и темы репозитория | Владелец | Administration у приложения или вручную (About ⚙) |
| Категории Discussions, закрепление | Владелец | Только интерфейс GitHub |
| Включение/отключение Discussions | Владелец | Settings → Features (сделано ✔) |

Пароли и токены в чат присылать **не нужно никогда**: настройка делается только кликами в указанных экранах.
