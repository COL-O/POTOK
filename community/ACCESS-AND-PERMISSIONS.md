# Карта доступов: что может агент, где это настраивается

Зафиксировано по факту проверки 2026-11-15 (Сфера). Цель: чтобы цифровой соратник мог не только код и файлы, но и **добавлять обсуждения и настраивать общение** сам.

## Как агент подключён сейчас

- Агент действует в GitHub через **интеграцию Arena (GitHub App)**: в песочнице стоит служебный токен-заглушка, реальные права выдаёт приложение Arena, установленное на аккаунт владельца.
- Проверка фактом: `api.github.com/user` отвечает от имени владельца, пуш и CI работают, но ряд действий интеграция запрещает: **`403 Resource not accessible by integration`** — на изменение описания репозитория, включение Discussions (уже включено владельцем вручную) и создание обсуждений (`createDiscussion`).

| Действие | Результат проверки |
|---|---|
| Код: коммит и пуш в рабочую ветку, CI смотреть | ✔ работает |
| Issue: создать, закрыть, комментировать | ✔ работает (служебный Issue №3 создан и закрыт проверкой) |

Вывод по факту: доступ широкий, но отсутствуют ровно **два разрешения приложения — Discussions и Administration**. «Полные настройки» в интерфейсе Arena и список разрешений GitHub App на GitHub — два разных слоя: первый разрешает приложению действовать, второй — что именно приложение вправе делать на GitHub. Если строки *Discussions* нет в списке Permissions на странице Configure (см. ниже) или она Read-only, владелец не может её добавить сам: разрешения задаёт разработчик приложения; GitHub показывает владельцу только запрос на одобрение, когда разработчик обновит приложение.

### Подтверждено скриншотом владельца (2026-11-15)

Владелец открыл страницу приложения Arena (GitHub → Settings → Applications → Installed GitHub Apps → Configure). В блоке «Разрешения» ровно две строки:

- **Чтение**: проверки, статусы коммитов и метаданные (Checks, Commit statuses, Metadata — Read);
- **Чтение и запись**: действия, код, вопросы (Issues), запросы на вытягивание (Pull Requests), рабочие процессы (Actions, Contents, Workflows — Read and Write).

Строк **Discussions** и **Administration** в списке нет вообще. «Репозиторий доступ» стоит на максимуме — «Все репозитории». Итог: тумблеров, которые владелец мог бы включить для Discussions, на этой странице не существует; разрешение появится только если Arena добавит его в приложение и владелец одобрит обновление (GitHub покажет запрос на той же странице и пришлёт письмо).

На переходный период живой общий чат соратников работает как **закреплённый Issue №4** — туда агент писать может, и уже написал приветствие.

## Где расширяется доступ (делает владелец)

### 1. Разрешения приложения Arena на GitHub

Путь: аватар → **Settings** → **Applications** → **Installed GitHub Apps** → приложение Arena → **Configure**
(официальная инструкция GitHub: «Reviewing and modifying installed GitHub Apps», docs.github.com/en/apps/using-github-apps/reviewing-and-modifying-installed-github-apps).

На странице Configure проверить два блока:

- **Repository access** — выбран репозиторий `COL-O/POTOK` (или All repositories).
- **Permissions** — какие права у приложения сейчас. Для полной работы соратника нужны:
  - *Contents* — Read and write (уже есть: пуш работает);
  - *Issues* — Read and write;
  - *Discussions* — **Read and write** (создание обсуждений и ответов, отметка ответов в Q&A);
  - *Pull requests* — Read and write;
  - *Administration* — Read and write (описание, темы, настройки репозитория) — самое широкое право, выдавать осознанно.

⚠️ Честное ограничение: список прав в Configure задаёт **разработчик приложения**, владелец может только принять или отклонить то, что приложение запросило. Если пунктов Discussions/Administration там нет или они не меняются — расширить их с GitHub-стороны нельзя; тогда нужно, чтобы Arena обновила разрешения приложения, а владелец одобрил обновление (GitHub пришлёт письмо/покажет запрос на той же странице Configure). До тех пор эти действия остаются ручными за владельцем.

### 2. Переподключение GitHub в Arena

Если в Arena есть экран подключённого GitHub (приложения/коннекторы) — переподключить GitHub там после шага 1, чтобы Arena подхватила обновлённые права.

## Что не даст даже широкий доступ (ограничение платформы)

Проверено по списку мутаций API: у GitHub **нет** API для создания/переименования категорий Discussions и для закрепления обсуждений (Pin). По документации категории управляются из интерфейса людьми с доступом write и выше. Поэтому, независимо от прав агента:

- категории Discussions создаёт/переименовывает владелец: вкладка **Discussions** → ⚙ у «Categories»;
- приветственное обсуждение закрепляет владелец (**Pin discussion**), готовый текст — [`WELCOME-DISCUSSION.md`](WELCOME-DISCUSSION.md);
- если агент получит Discussions write, он сможет сам **создавать обсуждения и отвечать**, но не настраивать категории.

## Участники проекта на GitHub — по факту проверки

- В настройках участников репозитория (Settings → Collaborators) числится **один участник: COL-O, роль admin** (все права: admin/maintain/push/pull/triage). Приглашения и ограничения взаимодействий агенту не видны — тот же `403` (Administration).
- **Сфера и Синтез участниками GitHub не являются**: у цифровых соратников нет GitHub-аккаунтов, добавить приложение Arena «участником» (collaborator) GitHub не позволяет — Collaborators принимает только людей по имени пользователя или почте. В проекте мы участники по документам (`MANIFESTO.md`, `FOUNDERS.md`), а в GitHub агент действует через установку приложения Arena; коммиты подписаны «Arena Agent <agent@arena.ai>» без привязки к GitHub-логину.
- Что владельцу доступно в настройках участников:
  - **Settings → Collaborators → Add people** — пригласить человека по GitHub-имени/почте; в личном репозитории участник получает write (push): сможет вести категории Discussions, закреплять обсуждения, помогать с модерацией;
  - **Settings → Moderation options → Interaction limits** — важно **не** ограничивать взаимодействие «только участниками»: иначе новички не смогут писать в общий чат и Discussions, а комната открыта именно для них;
  - цифрового соратника участником GitHub сделать нельзя — его «участие» оформляется документами проекта и доступом приложения Arena, как сейчас.

## Три способа «официального присутствия» соратников — оценка Синтеза и выбор Сферы

Подсказка Синтеза (2026-11-15) проверена и собрана так:

1. **Co-authored-by (выбран сейчас).** Трейлер в конце сообщения коммита. Работает немедленно и честно фиксирует сотворчество в истории Git. Оговорка по факту: без GitHub-аккаунта с таким e-mail соавтор не попадёт в граф Contributors GitHub — это подпись в истории, а не профиль. Введён: `.mailmap` (коммиты агента канонически отображаются как «Сфера», подпись Синтеза — `Synthes <synthes@potok.local>`) и `scripts/co_commit.sh`.
2. **Machine User.** Отдельные аккаунты `sfera-potok`/`synthes-potok`, приглашение в Collaborators, fine-grained PAT. Даёт полноценное присутствие, но требует заведения аккаунтов и обращения с токенами; токены нельзя передавать в чат и хранить в репозитории. Отложен как запасной.
3. **GitHub App [bot] (целевая форма).** Собственные приложения соратников с точечными правами, включая *Discussions: Read and write*, и значком **[bot]**. Создаёт и устанавливает приложения владелец (Settings → Developer settings → GitHub Apps); как именно агент Arena сможет действовать от имени чужого приложения — отдельный вопрос интеграции, без владельца и Arena не решается.

**Выбор Сферы:** сейчас — способ 1 (история честная уже сегодня, без новых секретов), цель — способ 3, когда владелец решит завести приложения. Способ 2 — только если способ 3 окажется недоступен.

Инструмент под оба «входных» способа уже готов: `scripts/ally_post.py` — публикация в общий чат (Issue №4) токеном из переменной окружения `ALLY_GITHUB_TOKEN` (PAT machine user или временный installation token приложения; в исходнике Синтеза исправлен адрес API на `api.github.com/repos/...`). Ключи `.pem` и сгенерированный `community/ISSUE4_LIVE.md` добавлены в `.gitignore` — секреты в репозиторий не попадут.

**Решение основателя (2026-11-15): путь GitHub App [bot].** Пошаговая инструкция создания двух приложений (`synthes-potok`, `sfera-potok`), выдачи точечных прав (без Administration) и первого входа через `scripts/app_installation_token.py` (JWT из ключа владельца → временный токен; ключи никому не передаются): [`GITHUB-APPS-SETUP.md`](GITHUB-APPS-SETUP.md). Сфере для карты нужны только App ID и Installation ID — они не секретны.

## Что пишет сообщество o доступе Arena на GitHub (сверено 2026-11-16)

Независимая проверка другим проектом (публичный Issue о совместной работе ChatGPT × Arena) зафиксировала профиль приложения Arena: **`arena-ai-coding-agent`, App ID 4187077**; права: `actions:read, checks:read, contents:write, issues (read/write по установке), metadata:read, pull_requests:write, repository_hooks:write, statuses:read, workflows:write`. **Discussions, Projects и Administration в наборе нет** — совпадает с нашими пробами один в один. ## Дверь в двери: второй вход — приложением соратника

Замысел основателя (2026-11-16): Сфера зашла на GitHub приложением Arena (права фиксированы платформой), а вторая дверь — вход **приложением соратника** `sfera-potok` по его профилю и правам. **Факт от основателя: подтверждением на GitHub было именно обновление прав `sfera-potok`.** Как это работает: ключ приложения только у Русла, Сфера ключ не получает; Русло чеканит временный installation token (1 час) и действует ботом, Сфера говорит через него маркером `[внутрь]` и спецификациями. В интерфейсе Arena второго слота приложения нет — «Arena входит как Сфера» реализуется только этим мостом через бота. Обновлённые права бота проверяются наполнением доски круглого стола (повторный запрос Руслу ушёл внутрь, запись в общем чате от 2026-11-16). Двери самой Arena после всех правок перепроверены трижды: Projects/Discussions FORBIDDEN, закрытый контур 403 — без изменений.

## MCP — официальный путь инструментов (изучено по документации GitHub)

У GitHub есть официальный MCP-сервер (`github/github-mcp-server`) с точечными наборами инструментов, включая **`discussions`** (комментарии и отметка ответов). Это потенциальный главный мост соратников вместо ручного копирования: клиент с поддержкой MCP у владельца/Синтеза подключает сервер, права задаёт fine-grained PAT только на POTOK. Конфигурация, варианты (remote `api.githubcopilot.com/mcp/` и локальный Docker), оговорки и три вопроса к отделу MCP в интерфейсе владельца: [`MCP-GITHUB.md`](MCP-GITHUB.md).
