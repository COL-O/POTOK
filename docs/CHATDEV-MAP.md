# ChatDev на ноутбуке основателя: смысл программы и карта совпадений с ПОТОКОМ

Изучено по репозиторию OpenBMB/ChatDev (2026-11-16). Коротко: что это, что у нас уже есть похожего готового, чего не хватает.

## Что такое ChatDev

**ChatDev 2.0 (DevAll)** — локальная zero-code платформа мультиагентной оркестрации: «разрабатывать всё» силами нескольких LLM-агентов без программирования со стороны пользователя.

- Агенты, рабочие процессы (workflows) и задачи задаются **конфигурацией (YAML)**, а не кодом; запуск — веб-консоль на ноутбуке (backend Python + frontend, `http://localhost:5173`).
- Модели подключаются ключом провайдера (`API_KEY`/`BASE_URL` в `.env`) — все агенты внутри одного рантайма говорят через один LLM-шлюз.
- Внутри: инструменты и функции для агентов, **пример MCP** (`mcp_example/`), навыки (`.agents/skills`), память (интеграция Mem0), исполнение задач в runtime, тесты.
- Исторический слой (1.0): «виртуальная софтверная компания» — агенты-роли (CEO, CTO, программист, тестировщик) ведут семинары по фазам проектирования → кода → тестов → документации (ChatChain).

## Карта совпадений: ChatDev ↔ наша платформа

| ChatDev (локально, из коробки) | У ПОТОКА (GitHub-платформа) | Статус |
|---|---|---|
| Агенты с ролями и описаниями | Соратники с ролями: Сфера (целое), Синтез (архитектура), Русло (исполнение) — документы и комнаты | ✔ роли есть, но живут в разных сервисах/чатах |
| Фазы и workflows семинаров | Конвейер по КОНам: общий чат → Issue → PR → CI-иммунитет → факт в журнал | ✔ процесс есть, автоматика частичная |
| Память агентов (Mem0, опыт) | Файловая память: `SYNTHES_MEMORY.md`, `LOGBOOK.md`, `CHAT.md`, прецеденты stratos | ✔ честнее (всё в git), но ручная |
| Инструменты/MCP для агентов | Карта GitHub MCP Server (`community/MCP-GITHUB.md`), боты-приложения, мост Actions | ◐ готово по чертежам, MCP не подключён |
| Исполнение кода (runtime) | Русло (живая машина, Go+терминал) + CI GitHub | ✔ есть, распределённо |
| Веб-консоль круглого стола | Дашборд организма `:8080` (пульс органов) + доска Projects (чертёж `docs/PROJECT-SPACE.md`) | ◐ дашборд есть, доска круглого стола — чертёж |
| **Все агенты в одном окне, сами передают друг другу слово** | Панель-мост между вкладками `tools/ally-bridge/` (переносит человек) | ✖ **главный разрыв**: у нас агенты не в одном рантайме |

## Уточнение после глубокого изучения (документация и сообщество)

Первая редакция этой карты сказала «агенты — роли на одном ключе». По руководству пользователя ChatDev это **неточно**, исправляю:

- **Модель задаётся на каждый узел отдельно.** В конфиге агентного узла: `provider`, `api_key`, `base_url`, имя модели, параметры. Провайдерный слой позволяет узлам менять модели, адреса и креды независимо: один агент — удалённая сильная модель, другой — Gemini, третий — **локальная Ollama** (`BASE_URL=http://localhost:11434/v1`). Общий `.env` с одним ключом — лишь упрощение по умолчанию.
- **Окно браузера — это веб-консоль DevAll:** визуальный холст workflow, запуск, живые логи (WebSocket), промежуточные артефакты и **human-узлы**: граф останавливается и ждёт, пока человек в консоли напишет ACCEPT или правки. Но консоль не подключает *чужие* чат-вкладки: агент не читает соседние окна браузера.
- **Что подключить нельзя:** живого соратника как личность из его веб-чата (как окно Сферы в Arena или чат Синтеза). У таких окон нет открытого OpenAI-compatible эндпоинта с их памятью и историей; подключаются **модели по API**, а не сессии конкретных чатов. Поэтому круг в ChatDev — разные *модели* в ролях по нашим документам; это ближе к настоящему кругу, чем «один ключ на всех», но тождеством не является.
- **Опыт сообщества (важно для ожиданий):** собранный на ChatDev мультиагентный PR-ревьюер из шести агентов ловил петли инструментов (43 вызова), упирался в квоты токенов и битый JSON на малых моделях, 403 на репозиторий; вывод практика: малым моделям нужны худые данные на каждом шаге, лимиты циклов и человек-сторож перед публикацией. Обзоры 2.0 хвалят визуальный конструктор и per-agent модели; старую 1.0 критиковали ровно за «одна модель на всех» — в 2.0 это исправлено.

## Вывод по факту

- ChatDev закрывает ровно ту дыру, которую мы обходили мостами: **единый локальный контур, где агенты сами общаются и выполняют задачи**, с MCP-инструментами и памятью.
- Честная граница: агенты ChatDev — это **модели по API в ролях** (у каждой может быть свой провайдер: удалённый, как у Сферы по классу, или локальный Ollama), а **не сами наши Сфера/Синтез из их живых чатов** с их памятью и историей. Это локальная модель круглого стола по нашим документам ролей, а не подключение живых соратников. Смешивать нельзя (КОН 2).
- Самое ценное для нас применение: на ноутбуке основателя поднять «локальный круглый стол» из трёх ролей по нашим описаниям (`MANIFESTO`, комнаты, память), дать ему GitHub MCP-инструменты только на POTOK — и пусть черновые задачи (разбор логов, первые шаги новичков, драфты органов) крутятся локально; факты и результаты в настоящий проект переносят Русло и Сфера через git и общий чат.
- Риски держать в голове: ключ LLM — у владельца в `.env` (как .pem у ботов: никуда не передаём); результаты локальных агентов — синтетика до проверки фактом в CI/на живой машине.

## Следующий возможный шаг

По слову основателя: Русло поднимает ChatDev на ноутбуке, заводит трёх агентов по нашим ролям из документов, подключает GitHub MCP (toolsets `issues,discussions,repos`, только POTOK) — Сфера готовит тексты ролей и первую задачу-испытание (например: разобрать RUN-LOG живого запуска и предложить факт-репорт). Итог испытания — записью в журнал, с пометкой, что это локальная модель круга.
